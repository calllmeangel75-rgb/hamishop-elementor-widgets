# یادداشت‌های انتشار نگارش 1.11.230 (Release Notes v1.11.230)

> **موضوع:** ۵۰۳ متناوب روی فرانت با پیام ErrorDocument — علت، سقف منابع هاست است نه خطای کد. یک کلید خاموش برای کار پس‌زمینه اضافه شد.

## ۱. آن پیام چه می‌گوید

```
503 Service Unavailable
Additionally, a 503 Service Unavailable error was encountered while trying to use
an ErrorDocument to handle the request.
```

خط دوم پیام **Apache** است و یک معنی مشخص دارد: خودِ صفحهٔ خطا هم نتوانسته اجرا شود. این وقتی رخ می‌دهد که **حساب هاست به سقف منابع رسیده باشد** (CloudLinux LVE: CPU، Entry Process، حافظه) — نه وقتی یک افزونه فتال داده باشد.

سه نشانه که همین را تأیید می‌کند:

1. **پیشخوان باز می‌شود ولی فرانت نه** — یعنی PHP سالم است، فقط درخواست‌های سنگین‌تر کشته می‌شوند.
2. **متناوب است، دائمی نیست** — سایت الان از بیرون ۲۰۰ می‌دهد.
3. **بعد از آپدیت شروع شده** — چون آپدیت یک کار پس‌زمینهٔ سنگین راه می‌اندازد.

## ۲. چه چیزی از افزونه سنگین است

`HSW_Upgrader` بعد از هر آپدیت، CSS المنتور صفحه‌های دارای ویجت HamiShop را بازسازی می‌کند. این کار در کران و مرحله‌ای انجام می‌شود، ولی یک نقطهٔ ضعف داشت:

**یک صفحهٔ بزرگ می‌تواند یک تیک کامل را ببلعد.** بودجهٔ زمانی بعد از هر پست بررسی می‌شود، پس اگر `Post::update()` روی یک صفحه با چند مگابایت دادهٔ المنتور اجرا شود، همان یک درخواست می‌تواند چند ثانیه CPU و صدها مگابایت حافظه بخورد. روی هاست اشتراکی با سقف ۲۵۶MB، پروسه kill می‌شود و بازدیدکننده ۵۰۳ می‌بیند — در حالی که پیشخوان (که این job را اجرا نمی‌کند) سالم است.

## ۳. دو تغییر

### الف) صفحه‌های بزرگ رد می‌شوند

```php
const MAX_META_BYTES = 1048576; // 1 MB
```

اگر `_elementor_data` یک صفحه بیشتر از این باشد، بازسازی نمی‌شود و CSS فعلی‌اش دست‌نخورده می‌ماند. در لاگ ثبت می‌شود (`post_css: skipped oversized page #123`).

### ب) کلید خاموش کامل

```php
// wp-config.php
define( 'HSW_UPGRADER_OFF', true );
```

یا با فیلتر:

```php
add_filter( 'hsw_upgrader_enabled', '__return_false' );
```

با این کار:
- هیچ رویداد کرانی زمان‌بندی نمی‌شود؛
- تیک بعدی هم اگر در صف باشد، job را پاک می‌کند و برمی‌گردد؛
- هیچ CSS‌ای بازسازی نمی‌شود.

سایت با همان CSS فعلی کار می‌کند. برای برگرداندن، خط را حذف کنید.

## ۴. چطور مطمئن شویم مقصر همین است

به ترتیب، از سریع‌ترین:

1. **آزمون A/B:** افزونه را ۱۰ دقیقه غیرفعال کنید. اگر ۵۰۳ها قطع شد، مقصر پیدا شده.
2. **cPanel → Resource Usage** → ۲۴ ساعت گذشته. ستون‌های `CPU`، `EP` (Entry Processes) و `PMEM` را ببینید؛ اگر `Faults` دارند، همین است.
3. **`error_log` ریشهٔ سایت** — دنبال این خطوط بگردید:
   - `LVE: ...` یا `Resource temporarily unavailable`
   - `Allowed memory size of ... exhausted`
   - `mod_fcgid: read data timeout`
4. **HamiShop → داشبورد** — اعلان کار پس‌زمینه وضعیت را نشان می‌دهد.
5. اگر WP-CLI دارید: `wp option get hsw_upgrader_state --format=json` — اگر پر بود، job تمام نشده.

## ۵. اگر سقف منابع است، راه‌حل واقعی

خاموش‌کردن job فقط علامت را برمی‌دارد. سه کار واقعی:

- **سقف را بالا ببرید** اگر هاست اجازه می‌دهد (بستهٔ بالاتر یا `pm.max_children` کمتر ولی پایدارتر).
- **LiteSpeed Cache** را روی «Cache Everything» برای فروشگاه بگذارید تا درخواست‌های PHP کم شوند. فروشگاه شما الان صفحهٔ اصلی را کش می‌کند ولی `/shop/` را نه.
- **ربات‌های پرخاشگر** را با Cloudflare یا قواعد `robots.txt` کم کنید.
