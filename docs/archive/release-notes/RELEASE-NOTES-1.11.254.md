# انتشار ۱.۱۱.۲۵۴ — اولین ذخیرهٔ ارسال رایگان

> **یادداشت تطبیق پس از انتشار:** این سند تاریخچهٔ زمان نگارش را حفظ می‌کند. PR #1 پس از تگ ۲۵۴ محاسبهٔ سبد را به ویجت‌های نمایش نرخ/خلاصه اضافه کرده است؛ ادعای پایین دربارهٔ اعمال‌نشدن این تغییر فقط وضعیت پیش از PR است. این تغییر در ZIP نسخهٔ ۲۵۴ نیست. وضعیت و محدودیت تست‌های فعلی: `docs/PROJECT-REVIEW-CHECKLIST.md`. هر دو تست ارسال فقط روی نصب دورریختنی ایزوله اجرا شوند، نه فروشگاه واقعی.

تاریخ: ۲۰۲۶-۱۱-۰۶

## ۱. ادعا درست بود

`add_option()` و `update_option()` دو hook جدا دارند. در ۲۵۳ فقط `update_option_{$option}` وصل شده بود، که تنها وقتی اجرا می‌شود که option **از قبل وجود داشته باشد** و مقدارش عوض شود. اولین ذخیرهٔ یک option که هنوز ساخته نشده از مسیر `add_option()` می‌رود.

بازتولید با مسیر واقعی وردپرس، قبل از رفع:

```
option حذف‌شده، اولین update_option( 'hsw_free_shipping_on', 'yes' )
  hookها      ["add:on"]
  نسخه bump    false      ← شکاف

option موجود، 'yes' → 'no'
  hookها      ["update:on"]
  نسخه bump    true
```

## ۲. رفع

هر دو hook برای هر دو option ثبت می‌شوند:

```php
add_action( 'add_option_' . $hsw_option, … );
add_action( 'update_option_' . $hsw_option, … );
```

## ۳. تست ماندگار در مخزن

`tests/qa/free-shipping-cache.php` — هشت بررسی، روی نصب واقعی وردپرس + ووکامرس:

```
HSW_WP_LOAD=/path/to/wp-load.php php tests/qa/free-shipping-cache.php
```

```
PASS  first save of the switch bumps the version
PASS  first save of the threshold bumps the version
PASS  switch on → off bumps the version
PASS  switch off → on bumps the version
PASS  threshold change bumps the version
PASS  unchanged save does not bump the version
PASS  the session cache key changes for the same package
PASS  a different package has a different key
```

**اعتبار تست:** با برداشتن hook `add_option_*`، دقیقاً همان دو بررسی اول fail می‌شوند — پس تست واقعاً همان شکاف را می‌گیرد، نه فقط تابع را صدا می‌زند.

## ۴. آنچه این تست پوشش نمی‌دهد

- **نشست مرورگری واقعی** با نرخ ذخیره‌شده و انتخاب‌شده: تست کلید کش را می‌سازد، ولی مرورگر و `WC()->session` واقعی اجرا نمی‌شود.
- **مالیات و نرخ انتخاب‌شده**: بعد از bump، انتخاب مشتری حفظ می‌شود ولی این رفتار در تست اندازه‌گیری نشده.
- **نشست دوم**: کلید مشترک است، پس هر دو نشست با یک bump باطل می‌شوند؛ ولی دو نشست هم‌زمان شبیه‌سازی نشد.

## ۵. یادآوری دربارهٔ پنل ویجت‌ها

سه خط اضافه‌شده در ۲۵۳ شفاف‌سازی رابط است، نه تغییر رفتار: توضیح می‌دهد «خاموش» چه معنایی دارد، ولی ثابت نمی‌کند صفحه‌ای که از ویجت خاموش‌شده استفاده کرده سالم می‌ماند. آن تست هنوز انجام نشده.

## ۷. دقت نام hash

نام `session key` گمراه‌کننده بود. تابع `WC_Shipping::get_package_hash()` **private** است و نشست CLI اصلاً چیزی ذخیره نمی‌کند. تست به `derived cache key` تغییر نام داد و در docblock نوشت: «همان فرمول روی همان ورودی‌ها؛ ثابت می‌کند نسخه بخشی از کلید است، نه اینکه ووکامرس نوشته است.»

## ۸. تست نشست واقعی

یک نشست مرورگری، بدون تغییر سبد، با تغییر option از داخل همان صفحه:

| مرحله | برچسب نرخ | ردیف خلاصه | shipping_total |
|---|---|---|---|
| خاموش (option حذف‌شده) | «نرخ ثابت ۲۵,۰۰۰» | «رایگان» | 0 |
| اولین فعال‌سازی (add_option) | «ارسال رایگان» | «رایگان» | 0 |
| خاموش | «نرخ ثابت ۲۵,۰۰۰» | «رایگان» | 0 |
| روشن، سقف بالاتر از سبد | «نرخ ثابت ۲۵,۰۰۰» | «رایگان» | 0 |
| روشن، سقف پایین | «ارسال رایگان» | «رایگان» | 0 |

**فهرست نرخ‌ها درست به‌روز می‌شود؛ جمع سبد در همان رندر عقب می‌ماند.** با `calculate_totals()` صریح، وضعیت هم‌سان می‌شود: `shipping_total=25000`, `cart_total=146000` و ردیف خلاصه هم ۲۵,۰۰۰ نشان می‌دهد.

**همین عقب‌ماندگی با تغییر خالص ووکامرس هم دیده شد:** تغییر هزینهٔ نرخ ثابت به ۳۰,۰۰۰ (بدون دخالت افزونه) نه برچسب را عوض کرد نه خلاصه را — چون انتخاب مشتری (`flat_rate:1`) ثابت مانده و هش سبد تغییر نمی‌کند. پس این کش جمع سبد ووکامرس است، نه چیزی که کلید افزونه ساخته باشد.

**تست‌نشده:** مالیات (فروشگاه `woocommerce_calc_taxes = no` دارد؛ برای تست باید روشن شود)، پرداخت واقعی، و دو نشست هم‌زمان.

## ۹. تست قابل تکرار (بعد از انتشار)

`tests/qa/shipping-session.php` — همان سناریو، این بار روی وردپرس/ووکامرس واقعی و در CI.

```bash
HSW_WP_LOAD=/path/to/wp-load.php php tests/qa/shipping-session.php
```

فیچر محصول، نرخ و آدرس می‌سازد و تلاش می‌کند در پایان تغییرات را برگرداند؛ پاک‌سازی تضمین مطلق نیست. فقط روی نصب دورریختنی و ایزوله اجرا شود، نه فروشگاه واقعی. دو اجرای پشت‌سرهم `ALL PASS` از گزارش همکار نقل شده است.

### ۹.۱ تفکیک دو اثر

قبلاً یک جمله بود: «لیست تازه می‌شود، جمع عقب می‌ماند». تست این را به دو پدیدهٔ جدا شکست:

| مرحله | لیست نرخ | shipping_total |
|---|---|---|
| نشست گرم، هزینه ۲۵,۰۰۰ | ۲۵,۰۰۰ | ۲۵,۰۰۰ |
| هزینه ۳۰,۰۰۰، بدون bump | **۲۵,۰۰۰** | ۲۵,۰۰۰ |
| هزینه ۳۰,۰۰۰، با bump | **۳۰,۰۰۰** | ۲۵,۰۰۰ |

**بدون bump، حتی لیست هم تازه نمی‌شود** — ووکامرس نرخ را از نشست می‌دهد. این همان کاری است که hook افزونه انجام می‌دهد (`get_transient_version('shipping', true)`)، پس bump واقعاً کار می‌کند.

**با bump، لیست تازه می‌شود ولی جمع نه** — `WC_Cart_Session::get_cart_from_session()` مقدار `cart_totals` را از نشست برمی‌گرداند و فقط وقتی محاسبه می‌کند که سبد عوض شده باشد یا مقدار ذخیره‌شده نباشد.

### ۹.۲ نقطهٔ درست محاسبه

سفارش سالم است، چون `HSW_Checkout_Complete::complete()` خط ۱۵۹ قبل از `create_order()` یک `calculate_totals()` می‌زند:

```
صفحه قبل از سفارش : نرخ ۲۵,۰۰۰ · shipping_total 0 · cart_total 120,000
سفارش #…          : shipping 25,000 · total 145,000 · method «HSW QA flat»
```

و خود ووکامرس در هر رندر صفحهٔ سبد و تسویه یک‌بار محاسبه می‌کند:

```
class-wc-shortcode-cart.php:96      // Calc totals.  → calculate_totals()
class-wc-shortcode-checkout.php:364 // Calc totals.  → calculate_totals()
```

ویجت‌های جامع افزونه این کار را نمی‌کنند؛ همین تفاوت است که عدد کهنه را در آن‌ها دیدنی می‌کند و در صفحهٔ شورت‌کد ووکامرس نه.

**پس نقطهٔ درست، رندر ویجت جامع است — نه `wp_loaded`.** محاسبهٔ مجدد روی هر درخواست یعنی اجرای فیلتر نرخ همهٔ افزونه‌های ارسال برای هر بازدید، از جمله REST و AJAX؛ همان الگویی که در HANDOFF به‌عنوان علت ۵۰۳ ثبت شده. این تغییر عمداً اعمال نشد تا هزینه و تداخلش با افزونه‌های ارسال (نرخ‌های API‌محور، وزن‌محور، جدولی) جدا اندازه‌گیری شود.

### ۹.۳ آنچه هنوز باز است

- مالیات — فروشگاه `woocommerce_calc_taxes = no` دارد.
- دو نشست هم‌زمان.
- پرداخت واقعی (سفارش با COD ساخته می‌شود، نه پرداخت واقعی).
- صفحه‌ای که از ویجت خاموش‌شده استفاده کرده.

## ۱۰. تصحیح تست — مبلغ سفارش بدون دست‌کاری

ایراد وارد بود: تست بعد از گرفتن سفارش `$hsw_order->calculate_totals( false )` را صدا می‌زد و بعد `shipping_total`/`total` را می‌خواند. یعنی مبلغ را قبل از اندازه‌گیری بازمی‌ساخت.

### ۱۰.۱ چه چیزی عوض شد

- آن خط حذف شد. سفارش با `hsw_sc_order_from_storage()` خوانده می‌شود: کش‌های `posts`/`post_meta`/`orders` پاک، `clean_post_cache()`، سپس `new WC_Order()` تا data store ردیف را دوباره بخواند. هیچ محاسبه‌ای، هیچ ذخیره‌ای.
- علاوه بر `shipping_total` و `total`، این‌ها هم ثبت می‌شوند: `shipping_tax`، `total_tax`، ردیف ارسال (نام/مبلغ/مالیات)، و متای خام `_order_shipping`، `_order_shipping_tax`، `_order_tax`، `_order_total`.
- سه بررسی تازه: ردیف ارسال با `shipping_total` سفارش هم‌خوان باشد، متای خام با آبجکت سفارش هم‌خوان باشد، و `total` با جمع ردیف‌های خودش برابر باشد (فقط وقتی مالیات خاموش است).

خروجی واقعی:

```
order #13845   : shipping 25,000 · shipping_tax 0 · tax 0 · total 145,000 · «HSW QA flat»
stored meta    : _order_shipping 25000 · _order_shipping_tax 0 · _order_tax 0 · _order_total 145000
shipping line  : HSW QA flat · total 25,000 · tax 0
```

### ۱۰.۲ ایمنی

- اگر `wp_get_environment_type()` مقدار `production` بدهد، اسکریپت **اجرا نمی‌شود** مگر `HSW_QA_ALLOW=1` ست شده باشد.
- پاک‌سازی به یک تابع منتقل شد و علاوه بر پایان اجرا، در `register_shutdown_function` هم ثبت است.
- تست شد: با یک استثنای عمدی بعد از ساخت fixture، PHP خطای مرگبار داد و فروشگاه **بازگردانده شد** (`flat_rate_1 = {"cost":"0"}`، `hsw_qa_shipping_product = NULL`، بدون محصول باقی‌مانده).
- محصول fixture با SKU `HSW-QA-SHIPPING` علامت‌گذاری می‌شود؛ بدون آن SKU نه بازاستفاده می‌شود نه حذف.
- **پروسهٔ kill‌شده قابل بازیابی نیست** — پس فقط روی محیط ایزوله.

### ۱۰.۳ آنچه این تست نیست

- **تست HTTP نیست.** `choose_shipping()` و `complete()` روی آبجکت صدا زده می‌شوند، نه از مسیر `rest_api_loaded`. ایراد سطح مسیر (permission، nonce، پارس JSON) اینجا دیده نمی‌شود.
- **تست مرورگری نیست.** اعدادی را که خلاصه می‌خواند می‌سنجد، نه HTML رندرشده را؛ قالببی که آن‌ها را نادیده بگیرد پاس می‌شود.
- «درخواست جدید» همان `get_cart_from_session()` در همین پروسه است، نه پروسهٔ دوم با کوکی.

### ۱۰.۴ باگ تجربهٔ خرید باز است

اگر صفحه هم‌زمان نرخ ۲۵,۰۰۰ و جمع ارسال صفر نشان بدهد، سفارش درست ثبت می‌شود ولی مشتری **قبل از ثبت** عدد اشتباه می‌بیند. این یک باگ تجربهٔ خرید است و باز می‌ماند.

دربارهٔ راه‌حل: «ابتدای رندر ویجت جامع» هم هنوز فرض است، نه نتیجه. باید سنجیده شود: رندر تکراری، چند ویجت در یک صفحه، نرخ‌های API‌محور، مالیات، و بازگشت از کش.

## ۱۱. دو محدودیت باقی‌ماندهٔ تست — رفع شد

### ۱۱.۱ پنجرهٔ خطر در پاک‌سازی

ایراد وارد بود: `hsw_sc_set_cost()` تنظیمات را می‌نوشت، و مقدار قبلی فقط بعد از **بازگشت** تابع در `$hsw_zone['original']` قرار می‌گرفت. خطا در آن فاصله = تغییر بدون نسخهٔ پشتیبان.

حالا مقدار قبلی **قبل از نوشتن** در یک رجیستری (`$hsw_originals['flat_rate'][instance_id]`) ثبت می‌شود، و `hsw_sc_restore()` از همان رجیستری می‌خواند نه از مقدار بازگشتی. متدی که خود fixture ساخته با `null` علامت می‌خورد و در بازگردانی حذف می‌شود (زون از `WC_Shipping_Zones::get_zone_by('instance_id', …)` پیدا می‌شود).

برای پنجرهٔ یک‌خطیِ بین `add_shipping_method()` و ثبت آن، `hsw_sc_sweep_orphans()` هر flat_rate با عنوان `HSW QA flat` را که در رجیستری نیست حذف می‌کند.

**تست پنجرهٔ دقیق:** یک استثنای عمدی داخل `hsw_sc_set_cost()`، **بعد از** `update_option` و **قبل از** بازگشت:

```
خطای مرگبار رخ داد (صفحهٔ error-page)
flat_rate_1 → {"cost":"0"}   ← برگشت
qa_product  → NULL
free_on     → 'no'
methods     → ۱ (بدون متد یتیم)
```

### ۱۱.۲ تخفیف دوبار کم می‌شد

فرمول قبلی:

```php
sum( item->get_total() ) + shipping + fees - get_total_discount()
```

`WC_Order_Item_Product::get_total()` همان `line_total` است، یعنی **بعد از** تخفیف. کم‌کردن تخفیف کل دوباره = دوبار.

حالا:

```php
sum( item->get_total() ) + shipping + fees
```

و اگر سفارش تخفیف داشته باشد، بررسی **رد می‌شود** با پیام صریح — چون هیچ سناریوی کوپنی این مسیر را نسنجیده و تیک سبز دادن آن حدس می‌بود، نه اندازه‌گیری.
