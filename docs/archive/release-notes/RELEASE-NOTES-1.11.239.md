# یادداشت‌های انتشار نگارش 1.11.239 (Release Notes v1.11.239)

> **موضوع:** اصلاح یک ایراد واقعی در شمارش پاسخ‌های تیکت که در ۱.۱۱.۲۳۸ وارد شد. بقیهٔ تغییرات ۱.۱۱.۲۳۸ دست‌نخورده‌اند.

## ایراد: شمارش پاسخ‌ها با پیش‌فرض وردپرس نمی‌خواند

در ۱.۱۱.۲۳۸ کوئری خروجی CSV را نوشتم:

```sql
AND comment_approved = '1'
```

ولی فراخوانی قبلی این بود:

```php
get_comments( array( 'post_id' => $id, 'type' => 'hsw_ticket_reply', 'count' => true ) );
```

`status` مشخص نشده بود، و در `WP_Comment_Query` مقدار پیش‌فرض `'all'` است (`class-wp-comment-query.php:310`). هسته، `'all'` را این‌طور ترجمه می‌کند (خط ۵۸۳):

```php
case 'all':
case '':
    $status_clauses[] = "( comment_approved = '0' OR comment_approved = '1' )";
```

یعنی **تأییدشده + در انتظار تأیید**، و اسپم و زباله نه.

نتیجه: اگر تیکتی پاسخ در انتظار تأیید داشت، عدد ستون «تعداد پاسخ» در CSV از ستون همان تیکت در فهرست پیشخوان کمتر می‌شد — چون آن یکی هنوز `get_comments()` را صدا می‌زند.

**رفع:**

```sql
AND comment_approved IN ('0', '1')
```

## اثبات — با همان حالتی که تست قبلی نداشت

یک تیکت ساختم و چهار پاسخ با وضعیت‌های مختلف در آن گذاشتم، با `UPDATE` مستقیم تا مقدار ذخیره‌شده همان باشد که تست ادعا می‌کند:

```
stored rows:
  #163 => '1'
  #164 => '1'
  #368 => '1'
  #369 => '0'        ← در انتظار تأیید
  #370 => 'spam'
  #371 => 'trash'

get_comments() : 4      (۳ تأییدشده + ۱ در انتظار)
reply_counts() : 4
verdict        : MATCH
```

با کوئری ۱.۱۱.۲۳۸ عدد **۳** می‌شد و اختلاف یک‌تایی می‌ماند.

> نکتهٔ روش: تست اولم `wp_insert_comment( comment_approved => 'spam' )` نوشت و وردپرس آن را به `'0'` نرمال کرد، پس تست اسپم و زباله را واقعاً نمی‌سنجید. با `UPDATE` مستقیم درست شد. همان اشتباهی که در تست قبلی هم بود: تست پاس می‌شد، ولی نه به دلیلی که ادعا می‌کرد.

## گارد در CI

دو چک تازه در `tools/ci-checks.php` (از ۲۰ به ۲۲):

- الگوی `comment_approved IN ('0', '1')` باید باشد؛
- الگوی `AND comment_approved = '1'` نباید برگردد.

بدون دیتابیس اجرا می‌شوند، پس در CI هم کار می‌کنند.

## پاسخ به دو نکتهٔ دیگر همان بازبینی

**دربارهٔ ایندکس در بند ۱** — حق با ایشان است که فقط `EXPLAIN` تصمیم می‌گیرد. اجرا شد، روی جدول `wp_options` با ۱۲۴۷ ردیف:

```
pattern    type     key            rows
old        index    option_name    1224
new        range    option_name    1
```

`type` از `index` (اسکن کامل ایندکس) به `range` رفت و تعداد ردیف‌های بررسی‌شده از ۱۲۲۴ به ۱ رسید.

**دربارهٔ فیلترها** — جایگزینی `get_comments()` با SQL خام، فیلترهای `comments_clauses` / `pre_get_comments` را دور می‌زند. درست است. برای یک خروجی مدیریتی پذیرفتنی است و در کد هم نوشته شده، ولی اگر روزی افزونه‌ای روی شمارش دیدگاه‌ها اثر بگذارد، این ستون از آن تبعیت نمی‌کند.

## آنچه تغییر نکرد

بندهای ۱، ۲، ۳، ۵ و ۶ بازبینی تأیید شدند و دست‌نخورده‌اند. دربارهٔ بند ۵: `bump_version()` روی `woocommerce_update_product` هم وصل است (نه فقط ایجاد و حذف)، پس مسیر عادی ویرایش محصول پوشش دارد؛ ورود دادهٔ مستقیم به دیتابیس یا ایمپورت‌هایی که هوک‌های ووکامرس را صدا نمی‌زنند، طبعاً هوک را رد نمی‌کنند.
