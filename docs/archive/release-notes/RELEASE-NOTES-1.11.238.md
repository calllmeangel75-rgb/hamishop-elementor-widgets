# یادداشت‌های انتشار نگارش 1.11.238 (Release Notes v1.11.238)

> **موضوع:** شش رفع کوچک بر پایهٔ بازبینی عملکرد. هیچ‌کدام تغییر رفتار قابل مشاهده ندارد؛ سه مورد از آن‌ها نقص واقعی بودند.

## ۱. پاک‌سازی transient با الگوی escape‌نشده

`includes/class-hsw-plugin.php`

```php
// قبل
WHERE option_name LIKE '_transient_hsw_lp_%'
```

در `LIKE`، کاراکتر `_` یک wildcard تک‌کاراکتری است. دو اثر داشت:

1. **تطبیق اضافی:** الگو `_transient_hsw_lp_%` رشته‌ای مثل `_transient_hswAlpB…` را هم می‌گرفت.
2. **ایندکس بی‌فایده:** چون الگو با wildcard شروع می‌شد، MySQL نمی‌توانست از ایندکس `option_name` استفاده کند و کل جدول `wp_options` را اسکن می‌کرد.

حالا با `$wpdb->esc_like()` ساخته می‌شود و با `$wpdb->prepare()` اجرا.

**اثبات روی لوکال** — دو گزینهٔ ساختگی، یکی هدف و یکی تصادفی:

```
old pattern matches : 2 row(s)   ← هر دو را می‌گرفت
new pattern matches : 1 row(s)   ← فقط هدف
```

## ۲. گزارش مشتریان طلایی فقط یکی از دو جدول را چک می‌کرد

`includes/class-hsw-wallet.php` — `golden_customers()`

کوئری `wc_order_stats` را با `wc_customer_lookup` JOIN می‌کند، ولی وجود فقط جدول اول بررسی می‌شد. اگر جدول دوم نبود — سینک نیمه‌کارهٔ Analytics، بازگردانی بکاپ — به‌جای فهرست خالی، خطای SQL می‌داد.

حالا هر دو با `esc_like` چک می‌شوند. تست: `rows: 3 | last db error: ''`.

## ۳. تشخیص HPOS با «وجود جدول»

`includes/class-hsw-products.php` — `best_seller_ids()`

فروشگاهی که HPOS را روشن کرده و بعد خاموش کرده، جدول `wc_orders` را نگه می‌دارد. کد وجود جدول را «منبع فعال سفارش‌ها» می‌گرفت و پرفروش‌ها بی‌صدا خالی می‌شد.

حالا از خود ووکامرس پرسیده می‌شود:

```php
OrderUtil::custom_orders_table_usage_is_enabled()
```

با `class_exists` + `method_exists` تا روی ووکامرس قدیمی خطا ندهد، و بررسی وجود جدول هم به‌عنوان لایهٔ دوم مانده.

## ۴. خروجی CSV تیکت‌ها: یک کوئری به‌جای یکی برای هر تیکت

`includes/class-hsw-account-support.php`

`get_comments( count => true )` داخل حلقه، برای هر تیکت یک کوئری می‌زد. خروجی ده‌هزار تیکت یعنی ده‌هزار کوئری.

حالا یک کوئری `GROUP BY comment_post_ID` در دسته‌های ۵۰۰تایی. خروجی CSV بایت‌به‌بایت همان است:

```
3 tickets compared, 0 mismatch
```

## ۵. بازهٔ قیمت فیلترها روی ذخیرهٔ محصول باطل می‌شود

`includes/class-hsw-products.php` — `bump_version()`

`price_bounds()` نتیجه را ۱۲ ساعت کش می‌کرد و هیچ‌چیز آن را باطل نمی‌کرد. محصولی که بالاتر از سقف قبلی قیمت می‌گرفت، تا انقضای کش با اسلایدر قیمت قابل انتخاب نبود.

حالا `bump_version()` — که از قبل روی ذخیره/حذف محصول و تغییر موجودی صدا زده می‌شود — transient را هم پاک می‌کند.

## ۶. جمع شارژ کیف پول یک‌بار در هر درخواست

`includes/class-hsw-account.php` — `wallet_topup_spent()`

صفحهٔ کیف پول دو بار امتیاز را می‌پرسد (کارت داشبورد + جعبهٔ تبدیل) و هر بار همهٔ سفارش‌های مشتری خوانده می‌شد. حالا نتیجه در همان درخواست memo می‌شود.

```
user 3 | points 1365 == 1365 | queries: first 21, second 2
```

عدد امتیاز یکی است؛ فقط پیمایش دوم حذف شد.

## آنچه عمداً انجام نشد

| مورد | چرا |
|---|---|
| بازنویسی کامل `wallet_topup_spent()` با SQL روی `wc_orders`/`postmeta` | عدد مالی را دست می‌زند و باید روی هر دو مسیر ذخیره‌سازی (HPOS و legacy) روی سایت واقعی سنجیده شود. فعلاً memo + همان منطق |
| خواندن `stock_status` از `wc_product_meta_lookup` | JOIN فعلی هم یک lookup روی ایندکس `post_id` است؛ سود اندازه‌گیردنی ندارد و وابستگی تازه می‌سازد. هزینهٔ واقعی آن بخش، `filesort` است که ذاتیِ مرتب‌سازی است |
| تغییر SQL مرتب‌سازی بر اساس درصد تخفیف | نتیجه از قبل در دو لایه کش می‌شود؛ بازنویسی کوئری بدون اندازه‌گیری، ریسک بی‌فایده است |
| `balance_gaps()` افزایشی و دسته‌بندی `install_tables()` | فقط مسیر مدیریتی/نصب؛ در استفادهٔ روزمره اجرا نمی‌شوند |
