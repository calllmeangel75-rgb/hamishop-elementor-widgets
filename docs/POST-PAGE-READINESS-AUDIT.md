# بررسی آمادگی صفحهٔ نوشته و فهرست مطالب

## وضعیت اصلاحات در این شاخه

- اصلاح‌شده و دارای تست خودکار: توضیح غلط بودجهٔ خزش و حذف nofollow لینک‌های فهرست؛ رزرو شناسه‌های موجود در متن و جست‌وجوی مقصد در همان مقاله؛ اعمال رنگ صریح بدنه به پاراگراف‌ها؛ پنهان‌کردن شمار ساختگی پسند؛ فیلد action فرم بدون JS؛ حذف قیمت قدیمی تکراری؛ اصلاح offset آرشیو؛ جلوگیری از نمایش فرم خبرنامه بدون مقصد؛ کنترل پارامتر تأیید دیدگاه. آزمون CI با WordPress/WooCommerce و آزمون مرورگری fixture موفق بود.
- هنوز باز: دکمه‌های فهرست در حالت بدون لنگر و سایدبار بدون JS کار نمی‌کنند؛ IDهای صریح تکراری نویسنده و برخورد با عناصر خارج بدنه، ترتیب کنترل‌های تایپوگرافی و بزرگ‌نمایی، صفحه‌بندی کارآمد دیدگاه‌های زیاد، امنیت/سازگاری واقعی فرم، قیمت متغیر/مالیات، و تست تمام استایل‌ها در سایت. فهرست پایین یافته‌های اولیه است، نه ادعای رفع تمام موارد.
- صفحهٔ تمرینی ارسال‌شده در خروجی متنی قابل دریافت بود: مقاله H1 و ۱۴ مورد فهرست دارد و بدنه نمایش داده می‌شود؛ این مشاهده تأیید DOM/CSS، کلیک، موبایل، زمان‌بندی یا ایندکس نیست.

## دامنه و اعتبار

بررسی ایستای کد شاخهٔ مبنا پس از PR #14: `widgets/class-hsw-widget-post-page.php`، `assets/css/hsw-post.css`، `assets/js/hsw-post.js`، کلاس مشترک وبلاگ، مسیر ثبت دیدگاه و نگاه تکمیلی به صفحهٔ آرشیو مجله. فرض اصلی ویجت «مجله: صفحه کامل نوشته» (`hsw-post-page`) است، چون فهرست مطالب دارد؛ صفحهٔ آرشیو جداست. این گزارش تست زنده، اجرای WordPress، بررسی CSS محاسبه‌شده، SQL یا بررسی ایندکس واقعی نیست و هیچ تغییری در سایت ندادیم. شواهد لازم: URL یک نوشتهٔ تمرینی، نام ویجت/قالب استفاده‌شده، خروجی صفحه با و بدون JS، موبایل/دسکتاپ، سایت‌مپ/کنونیکال و ابزار خزنده در صورت دسترسی.

## پاسخ دقیق دربارهٔ بودجهٔ خزش فهرست

گوگل عموماً fragment بعد از `#` را برای خزش/ایندکس به عنوان URL مجزا استفاده نمی‌کند. بنابراین تبدیل لینک‌های معمولی `#section` به دکمه و افزودن `nofollow` ضرورتی برای حفظ بودجهٔ خزش ندارد. مستندات رسمی: https://developers.google.com/search/docs/crawling-indexing/url-structure و https://developers.google.com/crawling/docs/faceted-navigation . این ادعا که هر مورد فهرست یک درخواست مستقل گوگل ایجاد می‌کند یا اینکه خاموش‌کردن لینک بودجه را حفظ می‌کند، توسط کد و مستندات پشتیبانی نمی‌شود. صفحهٔ واقعی همچنان یک درخواست خزش است؛ سایر URLهای واقعی (جست‌وجو، دسته، مرتب‌سازی، صفحه‌بندی) متفاوت‌اند. متریک crawl budget این سایت بدون Search Console/log قابل تعیین نیست.

کد کنونی: فهرست از h2/h3 محتوای فیلترشده ساخته می‌شود. حالت پیش‌فرض `none` برای فهرست اصلی و سایدبار دکمه با `data-target` می‌سازد و فقط با JS حرکت می‌کند. حالت `slug` و `index` در فهرست اصلی `<a href="#…" rel="nofollow">` دارند و سایدبار همچنان دکمه است. `data-nosnippet` روی هر دو ظرف برای محدودکردن استفادهٔ متن آن‌ها در snippet است، نه کنترل crawl/index صفحه. `show_toc` نمایش هر دو فهرست را خاموش می‌کند ولی رندر محتوا همچنان تیترها را پردازش و IDها را اضافه می‌کند.

**نقص قطعی توضیح پنل:** کنترل `toc_anchor` دکمه‌ها را برای «حفظ بودجه خزش» توصیه و متن نامعتبر دارد؛ کامنت مشابه PHP و JS نیز گمراه‌کننده است. `nofollow` برای fragment هم لازم نیست. توصیه: توضیح و کامنت را اصلاح کنیم، بدون تغییر بی‌خبر پیش‌فرض یا حذف تنظیمات ذخیره‌شده. طراحی مطلوب لینک واقعی با fallback بدون JS، قابلیت کپی/بازکردن در تب و ID ثابت جداگانه و با تست سازگاری انجام شود؛ لنگرها نباید به امید بهبود crawl budget به دکمه تبدیل شوند.

## یافته‌های P0/P1 صفحهٔ تکی

1. **پیمایش بدون JS:** دکمه‌های پیش‌فرض و سایدبار هیچ عمل بومی برای رسیدن به تیتر ندارند؛ نظر فایل JS که همهٔ TOC بدون JS کار می‌کند برای این حالت غلط است. لینک اصلی حالت slug/index بدون JS کار می‌کند. JS برای چند نمونه از `document.getElementById` استفاده می‌کند و ID تکراری/عنصر مشابه خارج محتوا می‌تواند به مقصد اشتباه برود؛ این سناریو باید تست شود.
2. **IDهای موجود/تکراری:** `prepared_content` شناسه‌های صریح دوباره‌تکرارشده را بدون حل تعارض حفظ می‌کند و فقط IDهای قبلی در مجموعهٔ `used` را دیده است. ID تولیدی یک تیتر می‌تواند با ID دستی تیتر بعدی یا یک عنصر دیگر در کل صفحه برخورد کند. ویرایش تیتر هم slug را تغییر می‌دهد و index با درج/حذف تیتر جابه‌جا می‌شود؛ تغییر خودکار ID دستی ممکن است لینک‌های منتشرشده را بشکند. regex روی HTML خروجی `the_content` کار می‌کند و باید روی محتوای ویرایشگر بلوک، شورت‌کد، نشانه‌گذاری غیرمعمول و تکرار تست شود؛ از کارکرد مطلق نمی‌توان مطمئن بود. متن فهرست از `wp_strip_all_tags` و escape ساخته می‌شود؛ entityها مانند `&amp;` نیاز به آزمون برای جلوگیری از نمایش دوگانه دارند.
3. **فرم دیدگاه بدون JS:** `comment_form_args` مقصد `admin-post.php` می‌گذارد ولی در کد widget هیچ فیلد مخفی `action=hsw_submit_comment` درج نشده؛ JS فقط هنگام submit با `FormData.set` آن را اضافه می‌کند. مگر اینکه افزونه‌ای فیلد را تزریق کند، مسیر بدون JS با action خالی endpoint اختصاصی را صدا نمی‌زند. ادعای progressive بودن نیازمند تست HTTP است. handler مشترک مهمان/واردشده از `wp_handle_comment_submission` استفاده می‌کند؛ سازگاری کپچا/اسپم/WAF و lifecycle و رفتار خطا/timeout باید با آزمون واقعی بررسی شود، نه دور زدن محدودیت امنیتی فرض شود.
4. **دیدگاه زیاد:** `get_comments` برای همهٔ نظرات تأییدشده بدون limit خوانده می‌شود؛ قبل از توابع لیست و صفحه‌بندی. بنابراین حجم داده و حافظه برای نوشته‌های پربحث می‌تواند بالا باشد، حتی اگر نمایش صفحه‌بندی شود؛ صحت صفحه‌بندی، تعداد، رشته‌پاسخ و تداخل کش را با تعداد زیاد/تنظیمات WP بررسی کنیم. بار واقعی اندازه‌گیری نشده است. پیام `unapproved` تنها با پارامتر GET نشان داده می‌شود و اثبات ثبت دیدگاه نیست.
5. **آیکون قلب موبایل:** سرور شمار *دیدگاه* را کنار قلب می‌گذارد و JS همان متن را `parseInt` می‌کند، در حالی که متن با ارقام فارسی تولید شده و parseInt آن را صفر تلقی می‌کند؛ بعد فقط پسند محلی مرورگر (`localStorage`) را تغییر می‌دهد. این شمارنده تعداد پسند واقعی نیست و ادعای اجتماعی غلط می‌سازد؛ bookmark هم محلی/مرورگر است نه حساب کاربر.
6. **کارت محصول:** `get_price_html()` ممکن است خودش قیمت قدیم/جدید تولید کند، ولی کارت قبلش نیز `<del>wc_price(regular)</del>` اضافه کرده؛ برای محصول حراجی می‌تواند قیمت قدیم تکراری و HTML تو در تو `<ins>` شود. درصد تخفیف از `get_sale_price()` خام محاسبه می‌شود، نه لزوماً قیمت فعال حراج/مالیات و فیلترهای ووکامرس؛ زمان‌بندی و متغیر باید آزمون شوند. انتخاب خودکار محصول از نام دسته/برچسب لزوماً ارتباط معنایی را تضمین نمی‌کند؛ موجودی، وضعیت انتشار/دیده‌شدن و قیمت روی محصول انتخابی نیز باید بررسی شوند.

## استایل و ریسپانسیو

- پالت پیش‌فرض از متغیرهای HamiShop در `.hsw-pp` می‌آید؛ `body_c` رنگ را روی `.hsw-pp__body` می‌گذارد، اما `.hsw-pp__body p` خودش `color: color-mix(...)` دارد. در نتیجه انتخاب صریح رنگ متن بدنه لزوماً به پاراگراف‌ها نمی‌رسد. رنگ تیتر h2/h3 هم جداگانه CSS دارد؛ تست کنترل‌های مدیر در CSS تولیدی Elementor لازم است.
- `body_size` روی بدنه متغیر می‌دهد و toggle اندازه همان متغیر را عوض می‌کند، اما کنترل تایپوگرافی `pc_p` مستقیماً روی پاراگراف و `li` هدف می‌گیرد و با default احتمالی CSS مستقیم می‌تواند اولی و بزرگ‌نمایی را بی‌اثر کند. `pc_h` با H2–H6 و گزینهٔ دیگر مقیاس عنوان/فهرست اشتراک دارد؛ تقدم و مقادیر ذخیره‌شده باید در Elementor تست شوند. `pc_h_gap` فقط h2–h4 را پوشش می‌دهد درحالی‌که تایپوگرافی h2–h6 است. عنوان مقاله نیز کنترل `a_typo('title')` مستقیم و `--hsw-pp-title-fs` دارد؛ کنترل‌های هم‌پوشان باید بازتولید و پس از رعایت backward compatibility یکپارچه شوند.
- استایل فهرست اصلی و سایدبار جداست. دکمهٔ فهرست استایل اختصاصی و focus دارد، اما اثر قواعد قالب، طول فارسی، RTL/LTR، کنتراست و هدف لمسی با مرورگر سایت تأیید نشده. h2/h3 `scroll-margin-top:80px` دارند ولی ارتفاع هدر چسبان واقعی فروشگاه می‌تواند بیشتر باشد. حالت حرکت کمتر در JS رعایت می‌شود.
- تصویر شاخص `large` با eager/high priority و کارت‌های مرتبط lazy هستند؛ اگر چند تصویر رقیب LCP باشند یا LiteSpeed تغییرشان دهد باید اندازه‌گیری شود. نوار بالا و dock ثابت/چسبان‌اند، کنترل تداخل با هدر و سایر پنل‌های موبایل، سایدبار و فونت‌های سفارشی نیازمند تست واقعی است.

## سئو، ایمنی و داده

- ویجت خودش H1 و محتوای `the_content` را رندر و H1 داخل محتوا را به H2 تبدیل می‌کند؛ قالب یا SEO plugin ممکن است H1/محتوا/اسکیما را تکرار کند. canonical، robots، sitemap، JSON-LD و وضعیت ایندکس توسط کل نصب تعیین می‌شوند؛ از بررسی این ویجت نمی‌توان صحت آن‌ها را ادعا کرد. تنظیم منبع روی «نوشتهٔ مشخص» در قالب تکی می‌تواند محتوای یکسان را روی نوشته‌های متعدد نمایش دهد؛ مسیر فعلی را ارزیابی کنید.
- برای محتوای رمزدار `post_password_required` قبل از متن اجرا می‌شود. منبع دستیِ پیش‌نویس/خصوصی برای کاربر فاقد `edit_post` رد می‌شود؛ بررسی استاتیک جایگزین تست مجوز و کش نیست.
- `popular_posts` بر اساس `comment_count` مرتب می‌کند، نه بازدید؛ صفحهٔ تکی آن را «پربحث‌ترین» می‌نامد. این ویجت فقط متای `hsw_post_views` را می‌خواند؛ در مسیر جست‌وجوشده شمارندهٔ افزایش پیدا نشد، بنابراین بدون منبع دیگر ممکن است شمار بازدید نمایش داده نشود. عکس‌ها/آواتار، لینک نویسنده، شرایط حریم خصوصی، اشتراک‌گذاری و فرم دیدگاه باید سنجیده شوند.
- بدون تست runtime، امکان قضاوت نهایی دربارهٔ امنیت HTML محتوا و همهٔ افزونه‌های متصل وجود ندارد. محتوای وردپرس از فیلتر `the_content` می‌گذرد؛ شورت‌کدها و افزونه‌های ثالث مسئولیت خود را دارند.

## صفحهٔ آرشیو مجله (مجزا از نوشته)

- فیلترهای `blog_cat`, `blog_sort`, `blog_s`, `blog_page` URL واقعی با query string می‌سازند؛ ترکیبات فیلتر/جست‌وجو/مرتب‌سازی می‌توانند URLهای متعدد ایجاد کنند، برخلاف `#`های TOC. canonical/noindex/robots را بدون بررسی نوع صفحات و نیاز به ایندکس یا آمار خزنده تجویز نکنید.
- در `blog-grid`، اگر `skip_first=yes` صفحهٔ ۱ و جست‌وجو خالی باشد، offset صفحهٔ اول یک واحد بیشتر است، ولی صفحهٔ دوم آن واحد را ندارد: برای ۶ کارت، رتبهٔ هفتم می‌تواند هم انتهای صفحهٔ اول و هم ابتدای صفحهٔ دوم تکرار شود؛ رفتار ویژه/فیلترها/تعداد یافته‌ها نیازمند تست WP و اصلاح با سازگاری است.
- فرم خبرنامه بدون shortcode و action مشخص به URL مجله POST می‌کند و در کد این ویجت handler اشتراک یافت نشد؛ به خودی خود اثبات ثبت ایمیل یا اتصال به سرویس نیست. اطلاعات شخصی در تست واقعی وارد نشود.

## ترتیب پیشنهادی

1. اصلاح ادعای غلط crawl budget بدون تغییر بی‌خبر حالت پیش‌فرض یا لینک‌های موجود؛ تست فهرست، پایداری شناسه، نبود JS و فیلدهای پیچیده.
2. رفع مشکلات واقعیِ خوانایی/تقدم استایل با حفظ مقدار تنظیمات موجود؛ برای عنوان، بدنه، فهرست، سایدبار و موبایل تست مرورگر و Elementor.
3. رفع شمارهٔ پسند، فرم بدون JS، بار دیدگاه‌ها و قیمت کارت پس از تست؛ نتیجهٔ تست روی یک نوشتهٔ تمرینی ثبت شود.
4. بررسی جداگانهٔ آرشیو، صفحه‌بندی و URLهای واقعی و خبرنامه؛ سپس سئو و کارایی نصب واقعی، نه نتیجه‌گیری از کد تنها.
